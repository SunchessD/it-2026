# Описание БД

## Назначение хранилищ

PostgreSQL хранит организации, учётные записи, приглашения, объекты, источники, партии импорта, отзывы, пороги, аномалии, их отзывы и оповещения. Это единственное место, по которому восстанавливают данные организации.

Redis хранит то, что можно собрать заново или что живёт только на время сеанса:

- сеанс входа;
- счётчик неуспешных попыток входа;
- ключ уже выполненного запроса сохранения;
- код подтверждения смены пароля и хэш нового пароля;
- JSON дашборда для пары «организация, ревизия, объект, период»;
- очередь идентификаторов партий, которую ждёт обработчик.

Пустой Redis после перезапуска не удаляет отзывы и не меняет действующий хэш пароля. Неподтверждённая смена пароля сбрасывается. Сеансы обрываются, пользователи входят снова. Дашборд на промахе считается запросом к PostgreSQL и снова кладётся в Redis. Партия со статусом `accepted` или `processing` остаётся в PostgreSQL, обработчик подхватывает её и без сообщения в очереди.

## Транзакции

Регистрация создаёт организацию, учётную запись администратора и строку порогов 2.00 / 2.00. Ответ об успехе уходит после COMMIT. Ошибка на любом шаге не оставляет организацию без администратора.

Смена имени обновляет `full_name` сразу. Смена пароля записывает `password_hash` только после верного кода из письма на email учётной записи. До подтверждения код и хэш нового пароля лежат в Redis, открытый пароль не сохраняется. Неверный или истёкший код оставляет прежний хэш.

Присоединение по коду повторно читает приглашение в той же транзакции, что и запись учётной записи. Новый email создаёт учётную запись с ролью аналитика. Если учётная запись уже есть в этой организации, вставка не выполняется: `organization_id` остаётся прежним, роль становится аналитиком. Отозванный код и учётная запись другой организации откатывают присоединение.

Приём CSV либо целиком вставляет партию и все её отзывы со статусом `accepted` и пустой тональностью, либо не вставляет ничего. Нечитаемый файл, пустой текст, лишний размер и лишнее число строк до этой вставки не доходят. Отзыв без даты входит в партию, `reviewed_at` остаётся NULL, `spam` остаётся NULL.

Обработчик переводит партию в `processing`, проставляет тональность, для датированных отзывов проставляет спам, при выполнении правила открывает аномалии и оповещения, ставит `ready` и увеличивает `data_revision`. Это одна транзакция на партию. Сбой до COMMIT оставляет прежние готовые отзывы и прежние статусы разбора. Партия остаётся `accepted` или возвращается к ней и не помечается `ready` или `failed`. Если обработка завершилась без тональности, транзакция фиксируется со статусом `failed`, с `failure_reason`, `started_at` и `finished_at`. Ранее готовые партии не меняются, `data_revision` не растёт.

Смена порогов:

```sql
UPDATE anomaly_threshold
   SET negativity_limit = $1,
       spam_limit = $2,
       version = version + 1,
       updated_at = now(),
       updated_by = $3
 WHERE organization_id = $4
   AND version = $5;
```

Ноль обновлённых строк порогов означает, что версия уже другая: строка организации на месте. Клиент получает сохранённые пределы. Новые пороги участвуют только в следующих проверках и не двигают `data_revision`.

Смена статуса аномалии заполняет поля разбора и в той же транзакции увеличивает ревизию организации:

```sql
UPDATE anomaly
   SET status = $1,
       version = version + 1,
       resolved_at = now(),
       resolved_by = $2
 WHERE anomaly_id = $3
   AND organization_id = $4
   AND version = $5;
```

```sql
UPDATE organization
   SET data_revision = data_revision + 1
 WHERE organization_id = $4;
```

Вторая команда выполняется только вместе с ненулевым обновлением аномалии. Ноль строк при аномалии этой организации означает другую версию: клиент получает её текущий статус. Отсутствие строки этой организации — отказ, чужое содержимое не читается. Статусы `confirmed` и `false_positive` требуют `resolved_at` и `resolved_by`.

`data_revision` увеличивается выражением SQL в транзакции обработки, переименования объекта или источника и смены статуса аномалии. Смена порогов ревизию данных не двигает: сводка отзывов от неё не меняется.

## Как обнаруживается аномалия

Длины окон — правило сервиса, не колонки. Короткое окно — 24 часа, базовый период — 14 суток непосредственно перед `window_start`. Граница конца не входит.

Конец окна — полночь UTC после суток, в которые попал самый поздний датированный отзыв партии по этому объекту. Начало — на 24 часа раньше. В окно и в базу попадают только отзывы с датой и уже проставленной тональностью.

Доли считаются отдельно для негатива и для спама. Аномалия этого типа открывается, если одновременно:

- в окне не меньше 5 отзывов;
- в базовом периоде не меньше 5 отзывов;
- доля в окне не меньше доли базы, умноженной на предел организации.

Если базовая доля равна нулю, вторая проверка пропускает любой положительный всплеск, но порог в 5 отзывов остаётся. Если базы меньше 5, строка аномалии не создаётся. Интерфейс не рисует это как нулевой негатив и не пишет, что поток нормальный.

Повтор того же объекта, типа и окна упирается в уникальный ключ. Негатив и спам одного окна — две строки. В каждой не меньше одного отзыва. Оповещение создаётся в той же транзакции.

Похожие тексты ищет обработчик среди датированных отзывов короткого окна: полное совпадение после схлопывания пробелов и регистр не учитывается. Результат пишется в `review.spam`. Пометка не означает установленное мошенничество.

## Дашборд и лента

Объём, доли, дни и источники считаются по отзывам с непустой тональностью. Условие периода: `reviewed_at >= начало AND reviewed_at < конец`. Отзыв без даты в этот запрос не входит. Если период в ленте не задан, отзывы без даты в ней видны.

Готовый JSON дашборда лежит в Redis под ключом `dash:v1:{organization_id}:{data_revision}:{object_id}:{from}:{to}`. `object_id` равен `all`, если объект не выбран. Срок ключа — 120 секунд. После роста ревизии старый ключ больше не запрашивается. Запись в Redis выполняется после COMMIT, общей транзакции с PostgreSQL у неё нет.

Текст запроса, которым заполняется кэш, лежит в [sql/03_queries.sql](sql/03_queries.sql). Параметры передаются отдельно от текста SQL.

## Redis

| Ключ | Срок | Содержимое |
| --- | --- | --- |
| `session:{id}` | 30 минут бездействия, срок продлевается | `account_id` и признак CSRF. Роль каждый запрос читает из `account` |
| `login:fail:{email}` | 5 минут, при десятом отказе не меньше 1 минуты | Число неуспешных входов одной учётной записи. Ключ по `lower(email)`, общий для входа и присоединения |
| `idem:register:{key}` | 24 часа | Идентификатор организации, уже созданной этим запросом |
| `idem:accept:{key}` | 24 часа | Идентификатор аналитика, уже созданного этим запросом. В начале запроса учётной записи ещё нет |
| `idem:{account_id}:{key}` | 24 часа | Результат уже выполненного сохранения: приглашение, объект, источник, партия, имя, подтверждение пароля, статус аномалии или пороги |
| `pwd:{account_id}` | 10 минут | Код подтверждения и хэш нового пароля. Открытый пароль не хранится. Верный код удаляет ключ |
| `dash:v1:...` | 120 секунд | Сводка, которую можно выбросить |
| `queue:import` | без своего TTL | Идентификатор партии. Список, не хранилище отзывов |

Значение сеанса и кэша — JSON. Неподходящая структура считается промахом. Открытый пароль, cookie и тексты отзывов в Redis не пишутся и в журнал не попадают. Код смены пароля в журнал не попадает.

## Резервное копирование и доступ

Раз в сутки `pg_dump` снимает базу в закрытое хранилище. Хранятся семь последних копий. Восстановление из исправной копии укладывается в 4 часа. Теряются только изменения после последней успешной копии. При восстановлении сохраняются связи объектов, источников, отзывов, аномалий и участников.

Учётная запись приложения не владеет кластером и не является суперпользователем. Ей даны права на таблицы схемы `reviewguard`. PostgreSQL и Redis слушают только внутреннюю сеть стенда. Секреты в репозиторий не кладутся.

Redis в копию исходных данных не входит.

## Проверки

1. Две организации. Запрос сводки первой не возвращает отзывы второй.
2. Составной ключ не принимает источник с организацией, которой нет у объекта.
3. Отзыв без даты сохраняется с пустым `spam`. Попытка поставить спам такой строке нарушает CHECK.
4. Повтор названия порогов вне диапазона 1…100 отклоняется.
5. Два сохранения статуса с одной и той же `version` — второе не меняет строку.
6. Обрыв транзакции обработки не переводит партию в `ready` и не увеличивает ревизию.
7. Сводка из Redis совпадает с запросом PostgreSQL. После новой готовой партии ключ со старой ревизией больше не используется.
8. Контрольный набор марта 2026 у организации «Север»: 11 датированных отзывов, 3 позитивных, 2 нейтральных, 6 негативных. Отзыв без даты и февральский отзыв в эту сводку не входят.
