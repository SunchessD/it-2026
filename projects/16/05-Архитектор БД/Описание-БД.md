# Описание БД

## Назначение хранилищ

PostgreSQL хранит исходные и служебные данные. Redis хранит только восстанавливаемую месячную сводку. При перезапуске пустого Redis исходные расходы остаются в PostgreSQL, а кэш заполняется при следующих чтениях.

## Таблицы и назначение полей

Типы, обязательность, ключи и индексы приведены в [физической схеме](Физическая-схема.md). Здесь описан смысл полей, которые используются в сценариях сервиса.

| Таблица | Поле | Назначение |
| --- | --- | --- |
| `auth_user` | `id`, `username` | Идентификатор владельца данных и логин для входа |
| `auth_user` | `password`, `is_active` | Хэш пароля в формате Django и возможность входа в аккаунт |
| `auth_user` | `date_joined`, `last_login` | Время регистрации и последнего успешного входа |
| `finance_revision` | `user_id` | Пользователь, которому принадлежит счётчик версии |
| `finance_revision` | `revision` | Версия расходов и категорий пользователя; входит в ключ кэша |
| `finance_category` | `id`, `user_id` | Идентификатор категории и её владелец |
| `finance_category` | `name` | Название, которое показывается в расходах и сводке |
| `finance_category` | `is_archived` | Запрет выбора категории для нового расхода; история сохраняется |
| `finance_expense` | `id`, `user_id`, `category_id` | Идентификатор расхода, владелец и выбранная категория |

| `finance_expense` | `created_at`, `updated_at` | Время создания и последнего изменения записи; не заменяет дату расхода |

При загрузке исходных данных сначала создаются пользователи, затем их ревизии и категории, после этого расходы. Сессии создаёт механизм входа Django. Redis заранее заполнять не требуется.

## Создание и изменение

При регистрации транзакция создаёт `auth_user`, `finance_revision` и две категории. Все изменения расходов и категорий выполняются через сервисный слой. В той же транзакции используется `UPDATE finance_revision SET revision = revision + 1 WHERE user_id = ...`. Вычислять новое значение счётчика в Python как «прочитать и записать плюс один» нельзя: параллельные запросы могут потерять увеличение.

При добавлении или смене категории сервис блокирует её строку через `select_for_update()` и проверяет владельца и архивный статус. Архивирование использует ту же блокировку. Так категория не может стать архивной между проверкой и сохранением новой записи. Ошибка ограничения целостности приводит к отмене всей транзакции и сообщению формы.

Удаление расхода физическое. Категория с историей только архивируется. Удаление аккаунтов и перенос данных между владельцами не входят в пользовательские операции первой версии.

## Запрос месячной сводки

```sql
SELECT c.id, c.name, SUM(e.amount_minor) AS total_minor
FROM finance_expense AS e
JOIN finance_category AS c
  ON c.id = e.category_id AND c.user_id = e.user_id
WHERE e.user_id = %(user_id)s
  AND e.expense_date >= %(month_start)s
  AND e.expense_date < %(next_month_start)s
GROUP BY c.id, c.name
ORDER BY c.id;
```

Параметры передаются драйверу отдельно от текста SQL. Месяц не подставляется строковой конкатенацией. Одна агрегация возвращает суммы всех категорий; общий итог складывается из этих же строк. Денежные значения переводятся в строку с двумя знаками только для показа и JSON.

## Ключ и значение Redis

Пример ключа: `expenses:v1:u:1:r:4:m:2026-10`. Значение хранится в обычном String как JSON:

```json
{
  "user_id": 1,
  "month": "2026-10",
  "total": "720.00",
  "categories": [
    {"id": 1, "name": "Продукты", "amount": "630.00"},
    {"id": 2, "name": "Транспорт", "amount": "90.00"}
  ]
}
```

Приложение проверяет структуру JSON, пользователя, месяц, формат сумм и совпадение итога с суммой категорий. Непригодное значение считается промахом. Запись выполняется одной командой SET с EX 60.

При попадании в кэш остаётся запрос ревизии к PostgreSQL. После расчёта при промахе ревизия проверяется повторно. Если она изменилась, этот результат не записывается в Redis. Отдельной общей транзакции между PostgreSQL и Redis нет.

## Резервное копирование и доступ

Резервируются PostgreSQL и конфигурация развёртывания без публикации секретов. Ежедневный `pg_dump` сохраняется в закрытое хранилище; сохраняются семь последних копий. Работоспособность копии подтверждается восстановлением в отдельную БД по NFR-09. Redis в процедуру восстановления исходных данных не входит.

Приложение подключается отдельной учётной записью БД с правами на свои таблицы. Миграции запускаются отдельно. PostgreSQL и Redis доступны только из внутренней сети развёртывания. Эти настройки проверяются при реализации, а не считаются уже выполненными.

## Проверки при реализации

1. Создать двух пользователей и их категории; попытка сослаться на чужую категорию должна нарушить составной FK.
2. Проверить суммы 0, -1 и больше предельной, пустое название и повтор названия с другим регистром.
3. Проверить запрет удаления категории с расходами и сохранение истории при архивировании.
4. Проверить границы месяца, включая декабрь и январь следующего года.
5. Вызвать ошибку внутри транзакции и убедиться, что расход и ревизия остались прежними.
6. Сопоставить результат сводки из кэша и из БД, затем повторить после изменения и отказа Redis.
